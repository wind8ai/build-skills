# 产品意图

build-skills 帮助用户把材料或已有 Agent Skill 整理成可执行的 Skill，并用任务结果判断是否需要改进。目标是让同一版 Skill 在用户选定的模型和场景中达到明确标准。

本文说明项目要解决的问题。阶段契约和实现边界见 [框架设计](design.md)，配置与命令见 [CLI 与配置](cli.md)。

## 先明确任务，再生成 Skill

用户提供材料和目标。准备阶段整理来源、适用范围、完成标准及验证场景，遇到无法确认的业务规则或假设时，列出问题供用户审阅。用户确认具体版本后，框架才开始构建。

默认准备提示要求模型利用可用的只读工具调查信息缺口，并为新增说法记录依据。调查能力取决于所配置模型及其工具；框架校验输出结构，不保证模型已经查证每条事实。用户仍需审阅来源、标准和场景。

## 用执行结果改进候选版本

Skill 的质量取决于它能否指导模型完成任务。框架让多个执行模型使用同一版 Skill 运行开发场景，再结合文件检查和模型评估判断结果。

开发评估未通过时，改进阶段根据候选内容、失败记录与评估报告生成下一版 Skill，然后重新执行。每轮保留候选版本及评估证据，便于检查改动依据。

多模型执行用于发现同一版 Skill 在不同模型上的表现差异。框架不要求多个模型分别生成候选，也不把各模型的平均分当作整体通过的依据。

## 用保留场景决定是否交付

开发场景用于改进，保留场景用于最后验证。用户在开始构建前审阅两组场景；框架不会把保留场景放入构建和改进阶段的模型输入。

开发评估通过后，框架用保留场景验证当前候选。只有验证通过且内容摘要一致的版本才能交付。结果只说明配置过的模型、任务和场景中的表现，不保证其他任务也能通过。

保留验证失败时，当前运行停止。继续优化需要新运行和新的保留场景。调用失败或预算耗尽时，框架保留已有结果，并按失败原因支持重试或后续处理。

## 将使用反馈带入后续运行

用户可以保存实际使用中遇到的问题。同一工作区的新运行会在准备阶段读取这些反馈，与本次提供的材料一起整理。框架不会自动把上一轮所有结论当作事实，也不会自动替换用户正在使用的 Skill。

## 当前范围

当前流程以可重复的本地文件任务为主，材料支持 UTF-8 文本和 Skill 目录。仓库示例使用确定性进程替身，验证确认、循环、恢复和交付等框架行为；它不调用真实模型，也不证明 Skill 的实际质量。

框架提供 Codex、Qoder 和自定义进程接入。真实模型、账号、工具权限与任务效果需要在用户配置下验证。独立工作目录有助于避免文件相互覆盖，但不构成操作系统沙箱。

## 参考依据

以下资料影响了项目的设计方向。build-skills 的实际行为以本仓库代码和文档为准。

- [Karpathy 的 LLM Wiki](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f) 提供了持续整理材料、保留来源与发现矛盾的思路。本项目将材料和使用反馈作为准备阶段的输入。
- [PStack 的 Eval 流程](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/eval.md) 强调用明确标准和盲评比较任务表现。本项目结合直接检查与匿名评估，记录每个模型的结果。
- [PStack 的验证 Skill 创建流程](https://github.com/cursor/plugins/blob/main/pstack/skills/create-verification-skill/SKILL.md) 围绕实际执行建立验证步骤。本项目采用验证通过后才交付的要求。
