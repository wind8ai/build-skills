# 框架设计

build-skills 是一个 Python CLI。它保存材料、确认记录、候选 Skill 和执行证据，按配置调用外部 Agent 完成构建与评估。单步命令和 `loop` 使用同一套阶段函数。

产品目标见 [产品意图](intent.md)，命令参数和配置示例见 [CLI 与配置](cli.md)。本文描述当前实现，不记录早期方案讨论或本机工具版本。

## 模块职责

项目采用单个 Python 包，固定使用 Python 3.12。uv 管理环境与锁文件，Hatchling 构建安装包。Typer 处理命令，Pydantic 校验数据，Jinja 渲染阶段提示，标准库 `tomllib` 读取 TOML 配置。

| 模块 | 职责 |
| --- | --- |
| `cli.py` | 解析参数，处理运行锁，输出结果与退出码 |
| `config.py` | 合并任务和模板配置，解析路径，检查模型引用与工作区边界 |
| `models.py` | 定义配置、任务场景、Skill 和评估结果的数据结构 |
| `workflow.py` | 管理阶段顺序、候选版本、预算与持久状态 |
| `workspace.py` | 保存材料快照，安全处理文件路径，校验 Skill 资源 |
| `evaluation.py` | 准备任务文件，检查执行产物，收集文件证据 |
| `providers/` | 组装外部命令，读取阶段产物，处理超时与进程清理 |
| `templates/` | 提供准备、构建、执行、评估和改进的默认提示 |

模板随包安装，运行时不依赖源码目录。框架采用本地文件和进程调用，不需要 Web 服务或任务队列。

## 配置与数据边界

任务配置声明目标、材料、工作区和模型配置，也可通过 `template` 引用共享模板。覆盖按顶层配置组替换，不递归合并子字段。未知字段、无效模型引用和缺失程序会在加载配置时被拒绝。

`workspace` 是必填路径。仓库内的运行只允许写入 `.build-skills/`，也可以使用仓库外的独立目录。框架拒绝材料与工作区相互包含，避免输出覆盖输入。材料与工作区的相对路径以任务配置所在目录为基准。

框架为每次运行保存材料快照及配置摘要。继续运行时会重新检查配置和材料；内容变化需要新建运行。反馈单独保存在工作区中，同一工作区下次 `prepare` 会读取这些反馈。上一轮候选如需继续使用，应显式作为材料提供或通过 `build --from-skill` 导入。

配置可能进入提示、调用记录或报告，因此不要把凭据写入命令参数、材料或提示模板。模型认证由外部 CLI 及其运行环境负责。仓库只包含框架代码、公开文档、通用示例和测试替身，运行数据留在本地。

## 阶段与候选版本

| 阶段 | 行为与结果 |
| --- | --- |
| `prepare` | 整理材料和反馈，提出范围、标准、开发场景、保留场景及需要用户回答的问题 |
| `approve` | 用 `--accept DIGEST` 确认用户审阅的具体版本；问题未解决时不能确认 |
| `build` | 生成首版候选 Skill，也可校验并导入已有 Skill |
| `execute` | 使用当前候选，按模型、开发场景和重复次数执行任务 |
| `evaluate` | 结合直接检查和匿名模型判断，生成当前轮的开发评估报告 |
| `improve` | 根据当前候选、原始材料和开发失败证据生成下一版候选 |
| `verify` | 仅在开发评估通过后执行保留场景，并生成验证结果 |
| `deliver` | 检查验证结论与候选摘要，导出通过验证的准确版本 |

`loop` 在准备后等待用户确认。确认后创建首版候选，再循环调用 `execute`、`evaluate` 和 `improve`。`improve` 已经完成下一版候选的生成与保存，之后直接回到 `execute`，不会再次调用 `build`。

开发评估通过后，`loop` 调用 `verify` 和 `deliver`。保留验证未通过时停止当前运行，继续改进需要新运行和新的保留场景。框架通过独立的阶段命令支持检查和恢复，不要求用户保持交互终端在线。

用户可在确认前编辑 `brief.json`，再用 `status` 获取新的摘要。构建开始后不能在同一运行中重新确认任务标准。`status` 展示当前状态、使用量和审阅摘要；`feedback` 保存使用反馈，供后续准备读取。

## 评估依据

每个执行任务使用独立目录，并加载同一候选 Skill。执行模型接收任务与所需文件，不接收评估标准或其他模型的结果。当前实现按顺序运行模型、场景和重复任务。

框架直接检查文件是否存在、文本是否相等及是否包含指定内容。评估模型一次接收当前阶段已完成的任务结果，使用匿名标签返回判断与证据。框架核对标签，拒绝缺失、重复或未知结果。

每个任务必须同时满足直接检查、模型通过判断和 `quality.minimum_score`。整轮要求所有任务通过。执行失败的记录会计为未通过，其他模型的高分不能抵消失败。

准备阶段提出开发与保留场景，用户在确认时审阅。构建和改进的模型输入不包含保留场景。框架不保证两组场景在统计上独立，用户需要判断保留场景是否提供了新的验证条件。

## 模型接入与权限

`providers` 声明程序、模型和权限，`roles` 将准备、构建、评估、改进阶段映射到 provider，`execution.models` 指定执行模型。角色可以共用模型，也可以分别配置。框架不预设真实模型或供应商预算。

Codex 使用非交互 `exec`，Qoder 使用 `--print`。适配器用参数数组启动程序，不经过 shell。`command` 接入可控外部程序或测试替身，通过 stdin 接收阶段、提示和结构化上下文。

构建与改进将完整文件写入 `skill/`，准备与评估写入 `response.json`。框架在本地校验这些文件，不依赖供应商的服务端 JSON Schema 功能。执行阶段保留文本、文件观察结果和调用日志。只有进程成功退出且产物通过校验，阶段才成功。

`permission` 默认为 `restricted`。Codex 映射到 `workspace-write`，Qoder 映射到默认权限模式；`full` 分别映射到两者的完整权限选项。自定义 `command` 的权限由程序和环境决定。

独立目录和不同模型输入不构成操作系统沙箱。完整权限的 Agent 可能读取目录外文件，因此保留场景隔离不是强制隔离。真实模型接入需要验证账号、工具、输出协议和任务效果，尤其是 Qoder 的实际运行行为。测试替身通过只证明框架契约。

## 预算、失败与恢复

准备、构建、执行、评估和改进各有调用次数与时间限制。执行预算按模型独立累计，跨场景和轮次使用。构建和改进默认不限制时间与调用数；执行默认单次 900 秒，准备和评估默认单次 600 秒。限制值为 `0` 时不限制该项，`max_rounds` 单独限制候选轮数。

框架在调用前预留额度，结束后结算时间，重试也消耗剩余额度。这些限制只覆盖框架启动的进程，不能推算供应商内部调用次数或费用，也不是计费上限。

一次运行只允许一个写入者。状态和产物保存摘要，改写产物时保留旧版本。外部调用超时或中断后，框架清理本次启动的进程组并保存调用证据；外部系统中的副作用不保证只发生一次。

单个执行任务失败后，框架继续其余任务，记录失败项并评估已有结果，随后停止自动循环。`execute --retry-failed` 和 `verify --retry-failed` 只重试执行失败项，复用已完成任务。已完成但质量未通过的任务不属于执行重试。

构建或改进正常退出后，如果文件因本地校验问题被拒绝，可用 `--recover-call` 重新校验对应产物。恢复会核对阶段、模型、提示和完整输入摘要，不重新调用模型。超时、中断、非零退出或输入变化的调用不能恢复为成功。

退出码、具体恢复命令及旧运行的处理方式见 [CLI 与配置](cli.md#失败与恢复)。

## 交付与验证

交付目录包含 `skill/` 和 `report.json`。Skill 包包含 `SKILL.md` 及其引用资源；报告记录模型、场景、评估、权限和验证限制。`deliver` 要求验证报告中的内容摘要与当前候选一致，重复交付时还会核对已有文件。

资源校验拒绝绝对路径、目录穿越、越界链接、冲突路径和未引用资源。Markdown 链接及命令中的明确相对路径都可以作为资源引用。完整运行目录不随 Skill 交付；分享报告前也应检查其中的任务输入和执行结果。

测试使用可控进程验证阶段行为、确认约束、预算、失败恢复、保留场景输入边界和交付摘要。GitHub Actions 在 macOS 与 Linux 上运行静态检查、测试、构建和仓库外安装验证，不运行真实模型或付费调用。
